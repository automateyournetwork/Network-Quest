## Account behavior

Opening/canceling the logout warning changes no runtime, session, API generation,
queued work or network request. A confirmed choice stops competing work before
POST logout. Its 204 must remain current through the API/controller microtask gap
and the final runtime CAS before memory clears. Logout/delete intentionally
advance API generation themselves, so returned generations are checked separately
from the application scope. Lost logout responses preserve the adventure and
remain unconfirmed. Only an explicit read-only current GET session can confirm
revocation by returning guest in this still-owned logout operation. A signed-in
result preserves memory and is never adopted as proof of the old account.

The warning accurately states that logout performs no implicit save; a save
already in flight may have committed. The UI neither claims that save was rolled
back nor reports it saved without an acknowledgement.

Deletion requires an explicit warning confirmation, a newly initiated same-provider
`delete-reauth` flow in a separate window, and another explicit Delete account now
choice. A postMessage hint only wakes AccountService's GET session. A session
observation does not claim fresh deletion authorization; the actual server's
same-account/recent-purpose proof remains mandatory for DELETE. Guest/different
provider observations cannot enable deletion or clear memory. Blocked popup fallback
and manual sign-in checks are explicit actions, never automatic auth restarts.

The final explicit DELETE creates 32 bytes through `crypto.getRandomValues` and
encodes one canonical unpadded base64url receipt. It remains only in the controller's
private volatile operation, never in projection/DOM/storage/URLs/error details.
If secure entropy is unavailable, no DELETE is sent. A successful current DELETE
204 confirms completion. An uncertain result sends no further DELETE or auth start;
it schedules only the narrow receipt-authorized status POST.

Status reads have at most six attempts over a 120-second window, backoff of
1/2/4/8/16/30 seconds, and honor Retry-After for automatic and explicit checks.
Backoff is installed before notifying subscribers. Pending stays pending; only a
current completed receipt confirms. Unknown/expired404, transport/error replies,
checking exhaustion and missing confirmation remain unconfirmed. Status checking
never reads progress, bootstraps auth or uses guest state as deletion proof.
Closing settings explicitly stops observation and discards the receipt, with text
explaining this consequence; no uncertain result is claimed rolled back. Explicit
later-account/new-adventure/restore views and disposal discard timers/receipt and
reject old responses. Both uncertain logout and deletion retain the adventure.

## Integration finding and coordinated resolution

GameApi's read-only status call correctly leaves API auth untouched. Unlike
logout/DELETE204, a completed receipt therefore requires the application to also
discard the old volatile API session identity/CSRF. `invalidate()` only aborts and
advances generation; `dispose()` clears session but permanently disables the
instance. This worker reported the gap to root and T050 and proposed a narrow
current-generation `forgetSession` operation or atomic API/service reconstruction.
Root approved and owns `GameApi.forgetSession(expectedGeneration):
ClientGeneration | null`: current-generation volatile clearing only, with no
network request or server-proof claim. Root also owns the actual Firefox finding
that `no-referrer` emitted an unusable Origin:null and the API referrer-policy
correction/native proof. T050 initially requested this component remain uncomposed
until its application handoff; root subsequently authorized this worker's scoped
composition. Shared accepted service changes remained root-owned; this worker
changed no GameApi source/tests. The actual join is verified below.
