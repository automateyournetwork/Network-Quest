`SaveCoordinator({api, store, validator, reader, requestId?})` composes the actual
accepted GameApi, SaveValidator, SaveReader and snapshot helpers. The store has
the existing synchronous `getState`/`compareAndSet` contract: swap state only,
then notify/render separately. The optional UUID generator is for deterministic
tests; runtime defaults to crypto.randomUUID and refuses reused local keys.

- `bindSession({clientGeneration,apiGeneration})` explicitly associates the
  authenticated runtime and verified API session. Their opaque counters need not
  equal each other. It requires each to be current and requires matching CSRF
  context; provider/display labels cannot establish account continuity. Binding
  resets volatile slot/receipt/consent metadata and takes the server's explicit
  autosave preference (false by default). A session summary alone is not a full
  slot read and cannot authorize a replacement.
- `captureView()` / `isCurrentView(token)` provide an owned lifecycle token with
  only runtime/API generations. Copies are invalid; invalidate/rebind makes old
  tokens invalid even when adventure IDs and counter values repeat. Capture before
  an asynchronous UI operation, then recheck immediately before applying its
  result. Successful save/read results also contain this token.
- `readSlot()` performs one serialized GET, accepting only the actual service's
  save-not-found404 as empty. For a200 it sends exact snapshotJson UTF-8 bytes to
  SaveReader, never JSON.stringify of unknown data. Supported validated original
  metadata must agree with its summary before use, including after migration.
  Results are opaque `SaveSlotReview` handles containing summary and reader
  result. All unsupported/invalid/interrupted/migration-failed results retain
  original bytes and block writes/replacement/autosave. The reader never changes
  the runtime adventure or server slot. A subsequent GET that discovers changed
  slot metadata enters reconciliation; merely learning a new ETag is not consent
  to overwrite another device's progress.
- `isCurrentReview(handle)` verifies owned review, live binding, same local game
  object and dirty generation, and no pending/read/write operation. Restore UI
  must additionally require `read.status === 'ready'`, obtain its discard-warning
  decision, and recheck this predicate immediately before replacing memory. The
  predicate alone does not authorize play of a blocked reader result.
- `authorizeReplacement(review)` is called only for the explicit UI decision.
  It captures a safe candidate and privately binds consent to the exact reviewed
  server adventure/ETag, local game/captured generation and lifecycle. Cloning a
  handle, re-reading, changing notes or starting another run invalidates it.
  Runtime replacementAuthorization is only the existing public projection; the
  coordinator's private owned consent is required and cannot be forged through
  that projection. A changed candidate requires a fresh read and decision.
- `save('manual'|'automatic')` captures the actual safe reducer state, without
  incrementing dirty generation, and performs one conditional prepared write.
  Empty-slot adoption and different-adventure adoption require manual action;
  automatic writes require the same adventure and enabled runtime/server
  preference. Snapshot safety rejects pending reducer work, dialogue/cutscene/
  transition/encounter/failure/shutdown states, and E03 as a current ending. E01/
  E02 require safe Continue anchors. Preparation checkpoints are never fallback
  snapshots. T051 owns safe-boundary triggers/debouncing; none is installed here.
- `retryPending()` uses the original frozen GameApi PreparedSaveWrite handle:
  exact body bytes, key, mode, condition and replacement header. It does not
  revalidate current new-write policy, re-capture newer edits or require the now
  current runtime to be a safe save boundary; it is resolving the already-safe
  captured operation. Network/timeouts/invalid responses and HTTP failures retain
  that handle and preserve gameplay/previous metadata. A later rejection cannot
  disprove an earlier lost receipt. There is no automatic retry or sign-in.
- `keepPlaying()` pauses new automatic writes and retains pending unknown outcomes.
  It cannot clear the frozen operation and thereby permit a new overwrite. Other
  read/save calls refuse while its outcome remains pending; explicit whole-view
  invalidation is the separate escape, never a declaration that a commit failed.
- A matching receipt must belong to the owned request/API/runtime generations,
  expected next conditional revision and matching current captured summary before
  the arithmetic acknowledgement helper runs. Only the captured dirty generation
  is acknowledged; concurrent reducer edits remain dirty. Receipt8/current9 is
  explicitly conflict/reconciliation, not Saved; knownSlot stays9. Both stale412
  and older receipts block further writes until fresh GET and explicit manual
  replacement consent. A new conditional replacement can still receive412.
- `invalidateView()` is mandatory before restore, New Adventure or account-view
  changes, including same-ID restores. It invalidates API requests, pending
  handles/captures/consent and this lifecycle, clearing only volatile persistence
  projections. It never mutates game/checkpoint/UI or claims the old operation
  failed. `dispose()` guards its terminal state before any subscriber runs.
- `state` and `subscribe` expose service events. Application renders should read
  the getter as well: reducer changes do not emit service events, and the getter
  projects Unsaved after post-acknowledgement edits. Conflict reasons are
  precondition, older-receipt and slot-changed. Per-send attempt identity protects
  the retry lock even when a failed-state subscriber immediately retries the
  same frozen operation. Notifications stop if a subscriber replaces their view;
  guards run again before I/O and after awaited results.
