## Recovery behavior

The PHP CLI takes consistent game and independent ledger snapshots, checks the schema and data, encrypts with separate keys, verifies authenticated readback, atomically promotes each complete archive and rotates its own copies after seven days. Scheduled cleanup uses the game's seven-day save acknowledgement expiry and the ledger's 24-hour confirmation expiry. Deletion markers, completion metadata and spent hashes outlive these receipts. The service can record bounded request metadata in a separate private hourly log. [Operations runbook](../../operations.md)

Disaster recovery requires the authoritative external ledger and rejects an existing or live destination. The tool applies pending and completed markers to the isolated candidate, removes restored sessions, and preserves the ledger's live confirmation state. Planned rollback also requires a durable drain and compares surviving current account, identity, preference, save and unexpired receipt rows. Earlier code that predates the drain still requires independent ingress and process isolation. ## Timed disaster rehearsal

On macOS 26.6.2 arm64 (Mac16,7), PHP 8.4.28, SQLite 3.54.1 and libsodium 1.0.22, one synthetic account made a real PUT through the local PHP application. It received HTTP 201 and revision 1. After capture, a second PUT received HTTP 200 and revision 2. After a deliberate short delay the harness removed the live DB from its configured location. A separate PHP CLI process restored into isolation. The observer reopened the candidate and matched the exact 856-byte payload at revision 1. The game database occupied 139,264 bytes and the authenticated game archive occupied 139,379 bytes.

These timings cover the local storage path and process startup.
