## Storage contract and APIs

`Database::open(string $file, array $documentRoots): Database` takes explicit
canonical absolute paths and a nonempty list of **all** applicable existing
document roots. It never discovers configuration or reads credentials. It requires
an existing accessible mode0700 directory outside every root and a mode0600,
regular, single-link database with the same owner. Missing files are exclusively
created under umask0077; caller umask is restored. It never creates/adopts/chmods
directories, repairs permissions, deletes existing data or loads private config.

Path traversal, noncanonical paths, symlink segments, hardlinks, public placement,
invalid permissions, file/directory inode replacement and unsafe sidecars fail
closed. Database/journal ownership must match the private directory; this does
not claim that `getmyuid()` identifies the effective process user. Trusted
operator-controlled ancestors are required. PHP path checks do **not** prevent
malicious same-UID processes or root from racing replacements between syscalls.
No ext-posix dependency was introduced.

The opener rejects malformed/non-rollback SQLite headers and WAL/SHM sidecars,
including a dormant WAL header with no sidecar, rather than silently converting
an existing WAL database. Private rollback journals are permitted for SQLite's
normal recovery and concurrent transactions. Observed settings are read back:
foreign_keys1, journal_mode`delete`, synchronous2/FULL, busy_timeout250ms,
trusted_schema0 and temp_store2/MEMORY. File identities and permission checks
repeat when obtaining a connection, before a write transaction and before commit.

`connection(): PDO` is for trusted repositories using prepared statements. Its
raw PDO capability is not a sandbox for hostile SQL. `immediate(callable)` owns
BEGIN IMMEDIATE/COMMIT/ROLLBACK and passes that PDO to a short synchronous callback.
It rejects nested helper calls and preexisting PDO/SQL transactions before
starting, preserves a caller's outer transaction on nested rejection, rolls back
on any Throwable (including Error or COMMIT failure), and propagates SQLite busy
errors. A failed BEGIN never rolls back another transaction. Callback authors
must not issue transaction-control SQL or external/provider calls; the helper
detects callbacks that ended its transaction and discards that connection, but
cannot undo a commit deliberately issued through raw PDO. If rollback itself
fails, discard the unusable connection; no success is returned.

`migrate(?array $migrations = null): void` is an **explicit** deployment operation,
not invoked by `open()` or a route. Default package contains version1 SQL. Tests
or a future reviewed package can supply trusted SQL keyed by consecutive integer
versions starting at1. Each exact SQL byte sequence has a SHA-256 checksum.
Unknown future versions, gaps or changed applied checksums fail before applying
anything. An unrecognized nonempty database without the migration ledger is
rejected. A single immediate transaction covers the entire new migration batch,
its ledger inserts and foreign-key check; SQL failure leaves no partial batch.
Successful repeats retain original timestamps/checksums and saved bytes.

Migration SQL deliberately supports a conservative subset: quoted text/comments
are excluded before rejecting transaction-control, ATTACH/DETACH, PRAGMA, VACUUM
and trigger-control tokens. Future triggers or migrations needing another mode
require a reviewed extension; callers cannot slip a COMMIT into a migration and
leave a silently applied prefix. Database migration versions are separate from
save-schema/content versions. This facility does not implement production backup,
release coordination, deletion-ledger reconciliation or downgrade/recovery policy.

The transaction decisions were cross-checked against the primary
[SQLite transaction documentation](https://www.sqlite.org/lang_transaction.html),
[PDO transaction-state documentation](https://www.php.net/manual/en/pdo.intransaction.php)
and [SQLite pragma documentation](https://www.sqlite.org/pragma.html). A pinned
runtime probe confirmed `PDO::inTransaction()` sees explicit BEGIN IMMEDIATE here;
the tests also exercise that behavior rather than relying on another driver's API.

## Schema and service obligations

Nine STRICT tables are dedicated to the game:

- `accounts`: opaque UUID, UTC creation seconds, active/deleting status.
- `identities`: one row/account, UNIQUE(provider, subject), BINARY/case-sensitive
  canonical subject; Google/GitHub only, GitHub positive decimal ID, optional
  display name. There is no email/token field and no email merging mechanism.
- `sessions`: hashed opaque identity and CSRF values, nullable account for guests,
  creation/activity/absolute-expiry/auth time and positive generation. Account
  deletion cascades to its sessions; session removal does not touch save rows.
- `auth_transactions`: one-use state-hash storage, initiating session, provider,
  login/delete-reauth purpose, expected account, Google nonce hash and private
  PKCE verifier, creation/expiry/consumed timestamps. FK cascades remove attempts
  with their session/account. Ten-minute maximum is stored as an explicit bound.
- `preferences`: one row/account with independent positive revision, autosave0
  by default, bounded audio levels/captions/motion/scale. Explicit account creation
  must insert this row in its transaction. Engineering defaults are volume1,
  captions-on, system motion, text scale1; only explicit choice enables autosave.
- `saves`: one row/account, positive bounded revision, server time, schema/content/
  adventure metadata, exact payload JSON text/hash and bounded summary JSON.
  It stores future JSON-object versions without forcing today's v1 interpretation.
- `write_receipts`: composite account/request UUID PK, fingerprint, committed
  revision/time, seven-day expiry. `acknowledgement_json` is a generated column
  containing only requestId/committedRevision/committedAt; it cannot accept an
  extra snapshot. Receipts deliberately have no FK to the current save revision:
  revision8 can remain acknowledged while the slot advances to9.
- `schema_migrations`: version, applied UTC seconds and exact SQL checksum.
- `operational_counters`: opaque hash bucket/period PK, bounded count and expiry.

Timestamps use integer Unix seconds (UTC); generated receipt committedAt is ISO8601
UTC. Internal UUID columns are canonical lowercase; services must validate and
canonicalize incoming UUIDs while preserving exact payload bytes for fingerprints.
Hashes are lowercase SHA-256 hex. Lookup/expiry/FK indexes support service access
and cleanup. Storage uses numeric flags for booleans and snake_case column names;
API mapping remains later work.

single-slot structure, SV-NETWORK-ROLLBACK atomic slot/receipt rollback, SV-BUSY
lock failure, PREF-UPDATE/defaults, SV-REPLAY-OLDER storage, SV-UNKNOWN-STORED exact
future bytes, AUTH-SEPARATE-OWNERS identity structure, and deletion/logout cascade
isolation. **All151 service cases remain behavioral-pending** in their independent
