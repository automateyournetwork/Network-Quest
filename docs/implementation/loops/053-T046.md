## Route and service composition

Both routes use the existing six-argument handler port:

```php
handle($method, $route, $rawQuery, $rawHeaderPairs, $bodyStream, $peerAddress): array
```

Exact method/path and an empty query are mandatory. `Security::headers` preserves
and rejects duplicate names, validates bounded syntax, and `Security::readBody`
with zero budget rejects any body, including account selectors. Nonempty bodies
receive413; malformed framing receives400. Trusted socket peer validation ignores
forwarded identity. Native TLS/Host/raw-field/slow-client admission belongs to the
existing shared transport, not an asserted property of a direct handler call.

`Account(Database, Sessions, Security, RecoveryAccountAccess, AccountDeletion)`
handles POST/logout and DELETE/account. Logout alone opens the concrete recovery
barrier, then requires exact Origin and session-bound CSRF. Existing guest
sessions may revoke their pending login attempts; unknown/expired sessions return
401 without bootstrap, refresh or login. Within the final short game transaction,
`Sessions::revokeWithin` repeats authorization and removes only the current
session. Foreign-key cascades remove that session's attempts and purpose proof.
Account identity, preferences, save bytes/revision, save receipts and other-device
sessions remain intact unless a separately authorized pending deletion must first
be reconciled by the mandatory recovery barrier.

Only after logout COMMIT succeeds does the204 response expire the exact configured
cookie name/path/Secure/HttpOnly/SameSite attributes. Errors never emit Set-Cookie.
Canceling the client warning sends no request; browser warning/memory/title
behavior remains T052/T056. No server save or implicit autosave is added here.

DELETE delegates directly to `AccountDeletion::delete(peer, rawFields)`, without
an outer barrier. Its actual T045 service owns exact Origin/CSRF/confirmation,
canonical256-bit receipt, account quota, final current-session authorization and
the same-account, same-session delete-reauth proof. A new ordinary login does not
authorize deletion. Proof ages299/300 seconds pass;301 and future proof fail.
The service owns the durable external intent, live-data/session commit and
completion marker, returning204 only after completion. A conflicting receipt is
fixed409; unexpected storage failures are private503, never false success. DELETE
does not issue a replacement/guest cookie or clear a later session cookie.

`DeletionStatus(DeletionReceipts)` has no Sessions, AccountDeletion or
RecoveryAccountAccess dependency. POST/account/deletion-status delegates directly
to the receipt service, which owns its external ledger lock and receipt/source
quotas. There is no outer/eager recovery call. Exact Origin and the canonical
receipt are the only authority. Incidental browser Cookie/CSRF headers are ignored;
they cannot select an account, gate status, refresh a session or confer authority.

Known receipts expose exactly `state` and UTC `expiresAt`. Pending200 suggests
`Retry-After: 2`; completed200 has no polling delay. Unknown and expired receipts
produce the same404 `deletion-unconfirmed` message/headers except independently
random request IDs. Receipt validity is half-open:86399 seconds remains valid,
86400 is expired. Pending/unknown/expired/session absence never claims completion.
Rate-limit429 preserves the actual positive Retry-After. Client bounded-backoff
and operation-view generation checks remain later UI work.

Every success/error uses existing no-store/no-referrer/nosniff/CSP/frame-denial
headers and server-generated request correlation. Receipt/status responses never
set cookies, redirect, expose ETags, provider identity, account UUID, notes, saves
or raw receipt bytes. Routes introduce no logging sink and collapse exception
details through `Security::problem`. Private production log configuration and
retention remain T165; quiet local diagnostics are not host logging acceptance.
