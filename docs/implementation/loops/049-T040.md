## Actual API and composition obligations

`GitHub(AuthTransactions, clientId, clientSecret, fixedHttpsCallback, ?clock,
?trustedHttpHandler)` takes explicit private configuration. The callback must be
canonical HTTPS, with the `auth/github/callback` suffix and no userinfo, query,
fragment or dot segments. The exact configured callback is reused for authorization
and code exchange. Real registration equality is still a provider/preflight check.
No caller-supplied endpoint, scope, return URL, environment lookup or token input
port exists. The handler is a trusted PHP test seam only, never a route/config flag.

`start(SessionContext, purpose='login')` returns `authorizationUrl` and integer
epoch-seconds `expiresAt`, matching Google's internal API. T041 must serialize
expiry as the wire contract's date-time string. The URL is fixed to
`https://github.com/login/oauth/authorize`, with `response_type=code`, exact callback,
shared state/S256 challenge and an explicitly present `scope=` parameter. No email,
repository, `read:user`, `offline_access`, login hint or nonce is requested.
For delete purpose it also requests `prompt=select_account`.

The shared `AuthTransactions` service owns random state/verifier creation,
session/provider/purpose/expected-account binding, ten-minute expiry and one-use
consumption. `GenericProvider`'s optional automatic `pkceMethod` setting is
deliberately unset: installed `AbstractProvider::getAuthorizationParameters`
would generate a different verifier when building the URL. Instead, the adapter
passes the shared S256 challenge explicitly to the real library URL builder and
calls its `setPkceCode(storedVerifier)` immediately before the real token exchange.
Tests verify the actual POST verifier hashes to the authorization challenge,
including two attempts completed out of order. The application's tested S256
path does not depend on the library generating a second independent secret.

`complete(SessionContext, state, ?code, ?error=null)` bounds and requires exactly
code or provider error, consumes matching state before any provider I/O, then uses
the real `getAccessToken('authorization_code', ...)` and `getResourceOwner(...)`.
Validated `access_denied` returns null, with no session/account mutation. Invalid
callback/state/replay/expired attempt or bad verification code fails400. Transport,
upstream status/body failures and provider configuration errors fail503. The fixed
`RequestRejected` message has no original HTTP exception chain or provider detail.
Failed provider attempts remain consumed and require another start.

The token response must supply a bounded nonempty string access token, case-
insensitive bearer token type and exactly empty string granted scope. A malformed,
missing or broader granted scope fails400 before any `/user` request. Refresh
tokens may be returned by an app configured for expiring tokens; they are never
requested, used or persisted. The real library may briefly hold them in memory.
The actual authenticated lookup is only `GET https://api.github.com/user` with
the token in the Bearer header, never a URL/query parameter or public username
lookup. JSON is requested explicitly with `Accept: application/json`; the fixed
User-Agent is `Network-Quest/1`, and the reviewed REST API version is2026-03-10.

Only a positive JSON integer `id` can establish the subject. It becomes a decimal
string without float conversion; numeric strings, booleans, zero, negatives,
fractional/overflow values and missing IDs are rejected. The verified 64-bit PHP
runtime preserves integers through PHP_INT_MAX; larger JSON integers fail closed.
Neither token `resource_owner_id`, email, login, name nor a response URL selects
ownership. Changed profile fields leave the subject unchanged. Optional `name`
is UTF-8, at most128 Unicode characters and control-free; invalid/missing names
become null. Valid names remain untrusted presentation text requiring text-only
rendering and a neutral public fallback in T041.

Success returns only this internal evidence array:

```text
provider: 'github'
subject: positive decimal string from authenticated /user.id
displayName: string|null
purpose: 'login'|'delete-reauth'
expectedAccountId: string|null (from the initiating session/transaction)
confirmedAt: integer server completion time
```

The transaction must still be unexpired after the provider roundtrip. No token,
email, complete profile, nonce or verifier appears in the return value. Accounts,
identities, preferences and saves are not created here. SDK/token/profile objects
are local and released on success/error; PHP does not guarantee physical
zeroization of all copied strings. No token persistence or logging is performed.

T041 must admit exact raw request structure, Origin/CSRF and rate limits, project
no-store public responses, redact callback queries before access/application logs,
and emit only an origin/source-safe completion hint. The adapter cannot undo
upstream web-server logging. Do not serialize its internal evidence to the browser.

After provider I/O, **inside the final short account transaction**, T041 must
recheck the original session with `Sessions::within`, honor the account-deletion
barrier, resolve `(provider, subject)` and rotate atomically. A callback can return
transient identity evidence after logout during HTTP; the test demonstrates the
actual final Sessions check rejects that stale context. No provider I/O holds the
database transaction. Account creation, cross-provider independence and final
session/callback behavior require the route tests, not this adapter result alone.

## Deletion confirmation and provider limits

Delete reauth starts a new purpose-bound provider roundtrip for the existing
session account; ordinary login is not deletion authorization. T041 must compare
the returned provider/subject with the expected existing identity and reject a
different selected account without creating it. If rotating, it must preserve
same-account purpose-bound completion proof on the new session atomically;
rotation deletes old-session auth attempts. T045/T046 must enforce the current
session/account, completion age no greater than300 seconds, explicit confirmation,
Origin/CSRF and the deletion receipt.

The GitHub account picker is an account-selection request, not proof of newly
typed credentials. No `auth_time`, `max_age`, forced password entry or stronger
provider-authentication-age guarantee is claimed. `confirmedAt` is the time of
this new validated roundtrip. A wrong selected identity may appear in internal
adapter evidence; only the required final account comparison can make it valid
same-account deletion proof. The test intentionally preserves that distinction.

No-scope GitHub tokens can read public information. This implementation confines
their use to authenticated `/user`; it does not call email, repository, contact or
other API endpoints. The dedicated app's actual grant/consent behavior remains
live-provider acceptance. Broader returned scopes fail closed locally.

Primary sources inspected on2026-11-26:

- [GitHub OAuth authorization](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)
  documents S256-only PKCE, the original verifier at exchange, JSON via Accept,
  explicit scopes, account selection and revalidating identity on each token.
- [GitHub OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)
  distinguishes no-scope public information from email/repository privileges and
  identifies the token response scope as the actual granted set.
- [GitHub authenticated user](https://docs.github.com/en/rest/users/users#get-the-authenticated-user)
  documents authenticated `/user`, its integer ID, public response without user
  scopes, and the current2026-03-10 REST version.
- Installed `GenericProvider`, `AbstractProvider`, `AccessToken` and
  `PostAuthOptionProvider` sources were read directly. No package was installed
  or patched; the adapter uses their actual request and response paths.
