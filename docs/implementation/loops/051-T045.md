## Storage protocol and lock order

The deletion artifact is a **separate private SQLite database**, not tables in the
game database and not a second player slot. It uses accepted `Database` private
path/file/journal checks, `journal_mode=DELETE`, `synchronous=FULL`, foreign keys,
short owned transactions and250ms SQLite busy timeout. Explicit document roots
and **all** game database backup/rollback roots must be supplied. The ledger and
its sidecars must be outside each supplied root. These checks cannot discover
operator backup jobs; actual coverage must be verified before production.

A distinct stable `<ledger-file>.lock` inode carries the shared EX `flock`.
Provision it explicitly as an empty0600 regular file with the same owner; no
request creates, replaces, chmods, renames or adopts a missing lock. Each use
checks mode, owner, one link and inode/device identity. The ledger directory is
0700, canonical, non-symlink and outside document/rollback roots through the
accepted Database boundary. Operator-controlled ancestors are required; this is
not a defense against malicious same-UID/root path replacement between syscalls.

The original attempted single-inode design failed on this actual Mac: while
`flock` was held on the SQLite inode, six tests failed with SQLite error5
`database is locked`, including SELECT. Moving the external lock to the separate
strict sidecar fixed this observed platform conflict. This was not inferred
from generic platform assumptions. Kernel-held lock tests verify contention,
bounded failure, release after exceptions and release after process termination.

Lock order is external `.lock` barrier, then **at most one** short SQLite
transaction at a time. External-ledger transactions finish before game database
transactions begin, and vice versa. `RecoveryAccountAccess::run` rejects entry
inside a game transaction. Nested external locking is rejected. Provider/network
IO must stay outside callbacks; the trusted deletion observer is a test-only
fixed-phase injection port, absent from production composition.

A protected account operation first reads every retained marker, including
completed markers, while holding the external barrier. It deletes matching live
accounts in one bounded game transaction, using foreign-key cascades for provider
identity, sessions, auth attempts, deletion proofs, preferences, save and save
receipts. Only after commit does it mark all pending completions in **one** external
transaction. It then runs the protected operation while the same external lock
is still held. No4096 independent synchronization transactions occur per request.
Completed markers are replayed too because a restored older game store may
contain rows deleted after its backup. Other account rows are preserved.

A failed reconciliation never runs the protected operation. Missing/inaccessible
ledger or lock, schema/policy mismatch, unsafe permissions, corruption, lock/busy
failures and storage exceptions fail closed. There is no permissive runtime gate
or initialization fallback. Startup composition can call `run(fn () => null)`;
every account operation must still use the gate because restored state and
concurrent requests require the same rule.

## Authorization, deletion and confirmation

`AccountDeletion::delete` owns one external barrier across its short phases.
It parses bounded duplicate-preserving headers, requires exact configured Origin,
current account session/CSRF, exact `X-Confirm-Account-Deletion:delete-my-account`,
canonical32-byte unpadded base64url receipt and existing account deletion quota.
The account UUID comes exclusively from server session state.

Final authorization rechecks the session inside the game transaction and requires
T041's `delete_reauth_proofs` row for **that session and that account**. Ordinary
`auth_time` or a new ordinary login never suffices. As clarified by root and the
independent fixture, proof ages299 and300 seconds are accepted;301 is rejected.
Future-dated proof is rejected. This inclusive five-minute proof rule differs
intentionally from half-open OAuth state and24-hour receipt expiry.

After authorization commits, while the same barrier prevents protected auth,
logout or save changes, one external transaction atomically inserts the account
intent, receipt hash/binding/24-hour expiry and hash-only spent-token entry.
Only then does a separate game transaction delete the account and cascaded data.
Only after its commit may a separate external transaction mark completion.
The204 result is constructed only after durable completion. A live/marker failure
produces no success. Once intent is durable, recovery completes deletion even if
the originating session/proof later expires; that authorized intent cannot reopen
an account. Both durable crash windows are handled without a session credential.

A receipt already bound to another account/operation returns fixed409 without a
new requested-account deletion intent. Admission counters/session touch and
reconciliation of a previously authorized unrelated intent are separate existing
obligations. No error exposes the conflicting account, token or progress.

`DeletionReceipts::status` accepts only the narrow receipt through existing exact
Origin/canonical token/receipt+source rate checks. It holds the external lock but
**does not invoke account reconciliation**. Its game transaction only updates
operational rate counters; it cannot create/sign in/delete an account. The
external lookup returns only `state` and UTC `expiresAt`. Unknown and expired
receipts both return null for T046's indistinguishable404. Pending is unconfirmed;
only completed indicates this authorized operation finished. Guest session state
plays no part. The service has no Sessions dependency. T046 owns fixed routing,
no body/query selectors, no-store HTTP/error projection and redacted transport.

## Retention, reuse and bounds

`DeletionRetentionPolicy(backupSeconds, restorationSeconds, evidenceReference)`
is mandatory, with no defaults. Both positive windows are bounded to ten years
each; their sum must exceed24 hours. Initialization records the explicit policy;
open verifies an exact match. A changed policy requires an explicit reviewed
operator migration, not silent request-time alteration. Synthetic tests use a
clearly labeled30-day backup plus7-day restoration policy. **This is not evidence
of GoDaddy's actual retention. Production remains unavailable until actual
reviewed coverage/policy and independent recovery storage are supplied.**

Markers store opaque account UUID, intent/completion times and a minimum
`retain_until` derived from that policy. This task never prunes a marker, including
one beyond its minimum. Longer retention is conservative against resurrection;
T165 owns reviewed maintenance and accurate player-facing retention explanations.
Receipt bindings are live only while `accepted_at <= now < expires_at`, with an
exact86400-second lifetime. Explicit `expireReceipts` removes expired binding rows
without touching markers; status does not perform maintenance.

Coordinator resolved the token-reuse lifetime explicitly: a **hash-only**
`spent_receipts` set remains after binding cleanup, with no account reference or
timestamp. It prevents a previously used token being rebound to a later account
once the24-hour binding is gone. It never proves status. T165 cannot remove that
set while claiming indefinite reuse rejection. This is logical-row retention,
not a claim of physical erasure from SQLite free pages, journals or backups.
No raw receipt, provider identity, credentials, note or progress enters the ledger.

The implementation bounds retained markers to4096 and spent hashes to65536;
capacity exhaustion fails closed and requires operator review. Marker reads use
LIMIT4097 to detect an out-of-policy artifact without unbounded result allocation.
An explicit later reviewed capacity/compaction scheme and host load/performance
measurement remain T059/T165 work; no production throughput claim is made.

## Concrete service API and integration handoff

```php
$policy = new DeletionRetentionPolicy($actualBackupSeconds, $actualRestoreSeconds, $reviewedEvidenceReference);
// Operator setup only: existing empty0600 file and <file>.lock in0700 directory.
$ledger = DeletionLedger::initialize($file, $allDocumentRoots, $allGameRollbackRoots, $policy);
// Runtime: existing initialized artifact and lock only. No discovery/create/migrate.
$ledger = DeletionLedger::open($file, $allDocumentRoots, $allGameRollbackRoots, $policy);
$accounts = new RecoveryAccountAccess($database, $ledger, $clock);
$deletion = new AccountDeletion($database, $sessions, $security, $accounts, $ledger, $clock);
$result = $deletion->delete($trustedPeerAddress, $rawHeaderPairs); // outside outer run
$status = (new DeletionReceipts($ledger, $security, $clock))->status($trustedPeerAddress, $rawHeaderPairs);
```

`AccountDeletionResult` carries status204/null fields or fixed409/code/message.
Admission failures remain `RequestRejected`; storage exceptions propagate to
`Security::problem`'s fixed503. No exception/SQL/token echo is permitted.
`assertScope` rejects composing AccountDeletion with a different database/ledger
than the concrete barrier owns. Ledger mutations are trusted internal ports and
require its lock; they are never route-level authorization or account selectors.

The T043 constructor now requires `AccountAccess` **immediately after**
`replaceableVersions`, before optional clock/observer/route. Save admission is one
gated phase, initial receipt lookup another, and final authorization/receipt/write
transaction another. Expensive schema/content validation and both fixed phase
observers remain outside the barrier. T044 must call `SaveRepository::write`
outside an outer gate to avoid nested acquisition. Receipt-first semantics and
final authorization still win over cached semantic errors and stale revisions.

T041 wraps bootstrap/session projection/auth phases with its same mandatory gate;
AuthTransactions owns its short gate portions separately from provider IO.
Sessions remains a leaf service using caller-owned transactions: injecting another
implicit gate there would cause recursive locking. T044 GET/preferences and later
T046 logout/deletion must use the same concrete recovery scope. Production route
