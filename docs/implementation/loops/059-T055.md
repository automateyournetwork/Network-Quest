## Crash windows and restore proof

Each crash worker opens its own actual Database and DeletionLedger. The parent
waits for an exact boundary signal, verifies the child's held kernel barrier,
sends signal9, and verifies actual termination by signal9. Bounded pipe/process
watchdogs and finally cleanup prevent a paused child remaining behind. The
before-intent pause is inside an actual session-update transaction; later pauses
use AccountDeletion's trusted, non-HTTP phase observer. No worker emits a success
response before being killed.

| Killed window | Observed live A | Receipt immediately after kill | Protected access |
| --- | --- | --- | --- |
| Before durable intent | Present; interrupted touch rolls back | Unknown404 | Existing save remains readable; no deletion claimed |
| Intent committed, live deletion not committed | Present | Pending200 | Recovery removes A before save read; read401, then completed200 |
| Live commit, completion marker not written | Absent | Pending200 | Recovery writes completion; read401, then completed200 |
| Completion marker written, response not returned | Absent | Completed200 | Read401; completion survives process loss |

While each durable-boundary child retains the external barrier, separate parent
connections can acquire/release `BEGIN IMMEDIATE` independently in both game and
ledger SQLite stores. This proves those SQLite transactions have ended; the
barrier remains continuously held. Nested barrier acquisition and acquiring it
inside an existing game transaction fail. Every broad RuntimeException catch
explicitly rethrows PHPUnit AssertionFailedError rather than swallowing an
assertion as expected contention.

Backups use actual SQLite `VACUUM INTO` an owned destination, followed by
`integrity_check`, `foreign_key_check` and expected slot-count verification.
Only this completed database-aware image is copied to a distinct restored path.
The external ledger and lock are not copied or replaced. Before protected access,
the restored graph equals the full predeletion graph. Status polling leaves that
graph untouched and the ledger bytes unchanged. A protected save read suppresses
A using the already-completed marker, never returns its private progress, and
preserves B's exact slot. Recovery DB and stable-lock inodes stay unchanged.

A separate long-retention schedule advances past the synthetic30-day backup plus
7-day restoration minimum, explicitly expires the24-hour receipt, restores the
predeletion image and still suppresses A. The completion marker survives exactly;
B's slot survives. This tests conservative marker behavior, not actual host
retention or operational backup tooling.

## Authorization, status and failure evidence

- A new same-account delete-purpose provider roundtrip rotates credentials and
  authorizes only the current session. Old session, ordinary login, another
  provider subject, another session's proof and revocation after admission do not
  authorize deletion. Wrong identity does not create/link an account.
- Expiring the session leaves both saves intact, denies DELETE401 and can yield a
  guest GET/session projection. The unknown receipt remains404 unconfirmed.
  Receipt-only requests cannot read a save, delete an account or begin deletion
  reauthentication; they cannot bootstrap a session.
- Pending polling with no cookie, the originating operation's cookie or a later
  account's cookie/CSRF returns only state/expiry and does not reconcile, delete,
  refresh, create, sign in or read progress. Pending markers remain pending and
  the whole account graph stays unchanged.
- Wrong/missing/null/trailing-slash Origins, missing/noncanonical/duplicate tokens,
  body/query account selectors and wrong method are rejected without reconciling
  a real interrupted pending intent. A well-formed unknown token is404.
- A receipt is valid at86399 seconds and expires at86400. Unknown and expired
  responses are identical after removing independently random correlation IDs.
  Explicit receipt maintenance removes the binding, preserves the completion
  marker and leaves the spent hash. A later reauthenticated account cannot reuse
  the old token either before or after expiry; it gets409 with its whole graph
  intact. A new receipt can authorize that later account's separate deletion.
- Thirty actual status polls consume a receipt's minute allowance; the31st is429
  even from another source. Sixty actual polls for distinct tokens consume the
  source allowance; changing only the token does not evade it. Retry-After is
  checked, the next minute resets admission, and stored counters contain neither
  raw source addresses nor receipt tokens. Three unauthorized-proof deletion
  attempts consume the account's hourly allowance; fresh provider reauth/session
  rotation does not reset it or create an intent.
- A real live-removal SQLite failure keeps receipt pending and denies save,
  preference and logout routes503 before account access. Removing the fault lets
  recovery finish. A real completion-marker commit failure returns503 after live
  removal, remains pending during status polling and denies protected access
  until completion can commit. Session absence is never substituted for receipt
  completion.
- Replacing the stable lock's inode makes deletion, save and status fail503;
  restoring the original owned inode restores ordinary behavior. The replacement
  is not silently adopted. Test-owned files are returned to their original inode
  paths before TestEnvironment cleanup.
- External persisted rows contain SHA-256 receipt hashes, opaque account binding
  and timestamps, with separate hash-only spent entries. File/response checks
  exclude raw receipts, session/CSRF credentials, provider-access sentinel text,
  private save notes and identity display text. Narrow responses are no-store,
  no-referrer and contain no Set-Cookie or redirect.
