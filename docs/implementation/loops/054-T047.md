## Result and integration interface

Implemented `src/services/game-api.ts` and `src/services/account.ts`, with their
two focused test files. These are real client service implementations, tested
through synthetic fetch/ReadableStream/window ports. **They are not composed into
the application yet and do not establish native browser, actual HTTP, real-provider,
durable-save, logout/deletion UI or aggregate G2 acceptance.**

`new GameApi({origin, apiBase, fetch?, timeoutMs?})` accepts an exact HTTPS origin
and a same-origin plain-segment API path. It has fixed methods only:
`getSession`, `startAuth`, `getSave`, `prepareSaveWrite`, `putSave`,
`patchPreferences`, `logout`, `deleteAccount` and `getDeletionStatus`. There is no
arbitrary route/header/token injection interface. Every request uses
`credentials:'include'`, `cache:'no-store'`, `mode:'same-origin'`,
`redirect:'error'` and `referrerPolicy:'no-referrer'`. The browser owns Origin and
Content-Length. Ordinary mutations use CSRF from the latest accepted GET session;
the deletion-status POST uses only its narrow receipt credential, even with no
session context. Incidental browser cookies do not become status authorization.

Bodyless mutations send `body:''`, following T041's actual host-framing finding,
so the browser can emit Content-Length:0 on HTTP/1.1. The service never sets that
forbidden header itself; GET has no body. The synthetic assertion proves the fetch
options, not actual browser HTTP/1.1 framing. T041/root own that native join.

Responses use a discriminated `ApiResult<T>`. Errors are `http`, `network`,
`timeout`, `invalid-response`, `invalid-request`, `session-required`, `stale` or
`disposed`. Unknown thrown errors are discarded, never logged/echoed. Known HTTP
problems retain only their validated contract shape and optional numeric
Retry-After; save 412 preserves the reviewed currentSummary. There is no automatic
retry, sign-in, write, destructive action or browser persistence.

JSON responses require no-store and JSON media type. Actual stream bytes are
bounded to 294912 (the 262144-byte slot plus envelope), nesting is bounded, decoding
uses fatal UTF-8, and a 15-second default request/body deadline is configurable only
within 1–30000 ms. Invalid/unconsumed bodies are cancelled. Session, preferences,
summary, acknowledgement, problem, conflict, start and status envelopes have
explicit field/type/value validation. Summary revision/ETag and save-response ETag
must agree. Preferences responses must also expose the actual service's HTTP ETag
matching their body revision/etag; matching metadata is returned to the caller.
An old replay acknowledgement may legitimately have committedRevision 8
and currentSummary 9; the transport returns both without claiming snapshot 8 is
still current. Frozen response objects cannot be edited into new session state.

GET save additionally returns two immutable strings:

- `rawJson`: exact decoded response envelope.
- `snapshotJson`: exact lexical snapshot value, including its internal whitespace,
  escaped strings and arbitrarily large future integer spelling. Surrounding
  envelope whitespace is excluded.

A bounded top-level scanner decodes member names and rejects duplicate envelope
members, including escaped snapshot/summary aliases, and duplicate summary keys.
It does not interpret or migrate snapshot semantics. T049 must pass
`new TextEncoder().encode(result.snapshotJson)` to T048's version-aware reader;
**never stringify the parsed unknown snapshot projection**. Unknown newer values
and numeric spellings remain available intact. T048's worker received this exact
interface. All supported-version/content checks remain with that reader/validator.

`prepareSaveWrite({bodyBytes, requestId, mode, precondition,
confirmAdventureReplacement})` captures the current client generation and clones
the bytes into a frozen readonly number array, retaining the exact UTF-8 string in
a private WeakMap. `putSave(prepared.request)` preserves body/key/mode/precondition/
confirmation across explicit retries. It validates byte/header syntax and size,
not current semantic policy: an old successful receipt must remain recoverable
after policy changes. Mutating the original byte buffer cannot change a retry.
A forged/cloned prepared handle is not admitted; a stale generation cannot send.
T049 owns dirty generations, serialization, consent, unknown-outcome recovery,
older-receipt reconciliation and any explicit construction of a new operation.

## Account generation and provider windows

GameApi retains volatile `session`, `capture()`, `isCurrent(generation)`,
`invalidate()` and `dispose()`. Invalidation aborts outstanding work and prevents
its data/errors from being published. GET session additionally orders concurrent
reads so an older reply cannot overwrite a later accepted session. The wire
contract exposes no stable account key: identical provider/displayName are never
treated as proof of account sameness. An unchanged session credential can retain
generation while preferences/slot metadata updates; changed CSRF, guest/auth state
or provider/display label advances it conservatively. A rotated token is installed
for subsequent ordinary mutations.

Only a current successful logout/delete 204 clears volatile API auth context.
Both recheck generation again immediately before that change, including the
microtask gap after the transport resolves. Unknown network outcomes do not claim
revocation/deletion. Receipt status never clears an account or implies completion
from guest state/404. A later account/view invalidation discards old status data.

`new AccountService(api, windowPort)` exposes `state`, `subscribe`,
`beginSignIn(provider, purpose='login')`, `openSignInTab`, `checkSession`,
`cancel`, `invalidateView` and `dispose`. `browserAccountWindowPort(window)` is
the actual browser adapter. Call beginSignIn directly from a user event: it opens
the blank provider window synchronously before session bootstrap or auth POST.
The original gameplay document is never navigated. A blocked popup returns
`popup-blocked` without starting auth; the later explicit Open Sign-in Tab action
reserves a new `_blank` tab synchronously before network work. No redirect URL is
offered in state/messages or persisted.

Only the server response's strict provider HTTPS endpoint is navigated:
Google `/o/oauth2/v2/auth` on accounts.google.com or GitHub
`/login/oauth/authorize` on github.com. Userinfo, explicit ports (including 443),
fragments, alternate hosts/paths/schemes and backslash/whitespace confusion fail.
The Google endpoint was checked against the installed actual SDK and existing
GoogleIdentityTest; GitHub against its implemented adapter. No security headers
are weakened. Severed/unreadable/closed browser references are not auth success.

Messages must have the exact configured origin, the exact retained window source
and exactly `{type:'network-quest-auth-complete'}`. They only wake GET session.
The final state is **`session-observed`**, with source hint/focus/manual; it is
never a provider-success or delete-purpose-proof assertion. A preexisting signed-in
session returned on focus cannot prove a new provider flow completed. GET session
has no deletion-freshness field; a future explicit DELETE remains server-authorized.

The service coalesces a valid hint arriving during an older focus check into one
delayed read, honors Retry-After, allows at most 12 session checks, bounds the flow
to the returned expiry/ten minutes and 600 one-second closure checks, and cleans
listeners/timers on disposal. Closure ticks do not poll identity. An observed
closed/unreadable provider handle can be COOP separation while OAuth continues:
it stops closure polling, becomes `unconfirmed`, and retains **manual GET session
recovery only**, within the original expiry and twelve-check budget. Focus/hints
do not automatically recover that lost handle. Explicit cancel still closes the
attempt and makes `cancelled`; no browser-handle observation claims cancellation
or provider success. Expired/exhausted recovery remains unconfirmed. A fresh explicit
choice is required to start another provider flow. Cancellation/failure leaves
adventure memory untouched; this module has no game/store/save-coordinator access.
Cancel is local cleanup, not a claim that a provider callback already committed
on the server has been undone. Subsequent identity still comes from GET session.

T050/T052 must bind account view changes, New Adventure/Restore and confirmation
decisions to invalidation and current-result guards. Canceled logout must make no
logout call/invalidation; confirmed revocation must clear actual adventure/checkpoint/
notebook memory and return to title without saving. Those UI/state behaviors are
not implemented or certified here. T052 also owns operation-specific deletion
receipt lifetime, bounded status polling and actual backup-policy copy.

   Guards after state notifications fixed this; cancelled views cannot start
