# Deploying the Spec001 game package

The website operator receives a versioned game archive and its SHA-256 through the release handoff. The only website-owned game integration is a detail page at `/arcade/network-quest/` linking to `/arcade/play/network-quest/`, plus the mapping of that play path to the verified public game directory. The open same-host staging checks and the measured local results are in the staging record. [Staging evidence](evidence/spec001/staging.md) · [Package integration](../release/INTEGRATION.md)

## Receive and stage a version

1. Read the manifest and compare the candidate identity and archive hash with the coordinator's release record. On receipt, verify the archive against that trusted SHA-256. Extract into an empty, version-specific directory outside every document root. From there run `python3 tools/release-archive.py verify .`. This verifies every file and the full name inventory. A failed check keeps the previous public target in service.
2. Measure available disk space and inodes against this extraction, the prior version, package transfer, backup, restore and migration needs. Record the actual hosting allowance and headroom. Prepare the current shell, API and rollback target as a matched set. Where available, use a verified same-filesystem atomic link switch for the game's public directory. If the host requires copying files, prepopulate a separate complete public game directory and switch the mapping under a game-scoped maintenance window. Avoid copying over a directory that is serving requests.
3. Use the staging origin and prefix registered for the game, with dedicated test registrations, accounts, storage, keys and job configuration. Bind the game prefix, version-specific PHP path and private SAPI settings as a unit. Test through HTTPS with certificate and hostname verification. Other processes, roots and rewrites on that origin retain their existing configuration. [Host checks](evidence/spec001/host-probes.md) · [Provider preflight](evidence/spec001/provider-preflight.md)

| Location in or alongside the extraction | Operator mapping |
| --- | --- |
| `public/arcade/play/network-quest/` | Mount only this directory at the corresponding play URL. Preserve dotfiles during transfer. Its shell, credits, media, bundled scripts, `release.json` and `api/v1/index.php` must match the verified version. |
| `private/server/` and `private/specs/` | Keep together outside all webroots. The PHP front controller loads the packaged game and its production dependencies. The service reads the packaged migrations, save policy and schema at their fixed relative locations. |
| Root licenses, `SHA256SUMS`, `release/`, `metadata/`, `tools/`, `docs/`, `assets-src/` | Retain as private release materials for verification, support and source retrieval. The game's public credits remain accessible under the play URL. |
| Operator configuration, writable game database, independent deletion ledger, keys, archives, logs and restore workspace | Supply canonical private paths outside each public root and version directory, with independent recovery storage and keys. The public version pointer can move without moving these records. |

The fully extracted layout lets the front controller find its PHP code by location. For a separately placed public tree, set `NQ_PACKAGE_ROOT` to the exact private extraction root in the trusted game SAPI. Point `NQ_CONFIG_FILE` at the private, single-linked, mode-0600 JSON configuration in its mode-0700 parent. Supply every canonical document root via `NQ_DOCUMENT_ROOTS_JSON`, accounting for publicly mapped directories as well as the site root. First-time private initialization and migrations are deliberate operator actions. Exclusively create the empty mode-0600 ledger file and adjacent empty mode-0600 `.lock` file before initializing the independent ledger. Match the API/content/save/DB versions in the candidate manifest and preserve migration checksums. Use the packaged examples, production PHP executable and private recovery procedure. ## Route and cache checks

Keep the package's game-local `.htaccess` and the host's verified LiteSpeed PHP handler together. Route the original URI, method and query for the complete nested `api/v1` namespace to its single PHP entry point. Do not redirect API requests into the HTML game. Require support for the supplied rewrite, header, directory-index and option directives or configure their equivalent scoped to this game. On the local Apache 2.4 fixture, the game directory required explicit permission for MultiViews via `AllowOverride FileInfo Indexes Options=Indexes,MultiViews`. Its parent allowed FollowSymLinks for the tested cutover and rewrite. Disable listings and MultiViews, deny requests for Apache control files, and serve the correct MIME types for JavaScript, CSS, images, audio and GLB. Confirm that the HTTP handler executes the game PHP front before routing traffic to it. The production service admits the previously verified LiteSpeed boundary. Generic FastCGI SAPIs return unavailable on configured stateful requests. [Transport checks](implementation/hosting-header-admission.md)

Verify the active play path in a fresh browser and check actual GET responses. The shell, manifest, credits and stable media require `Cache-Control: no-cache`. Fingerprinted JS/CSS may return `public, max-age=31536000, immutable`. Every API success, error and callback requires `no-store`. Verify a backend outage in isolated staging too. Stop the staging game worker, request session, save and both callback paths, and check for exactly one `Cache-Control: no-store` on each gateway-generated 503. The site must still serve its normal static bytes and headers. Restart the worker and repeat normal game checks. Keep these headers through intermediary caches. The HTML shell permits only same-origin scripts. Each callback owns its separate script policy. Redact raw callback queries, cookies, CSRF values, receipt headers and request bodies in the front-end server as well as the game service. Retain a recoverable prior release and account for already-open tabs using the prior version's fingerprinted chunks at cutover. [Delivery contract](../specs/001-physical-layer-underworld/contracts/delivery.md)

## Verify the host before release

- Record the hosted version and compare its release manifest and served asset bytes with the verified archive. Enter the game through the staged detail link. Start a guest adventure in the Arrival Lift, close Scene, press W, and click the visible Titan's Workshop label on the room image. Verify that The Titan's Workshop opens and its room art loads. Exercise reload and failure recovery through the staged game. Compare the chosen arcade listing, another game, analytics health and certificate-validation routes with their read-only baselines. Use route status, stable content or a version fingerprint appropriate to each surface. For a changing live analytics store, use an existing aggregate read-only health check and verify that game configuration, paths and jobs target their dedicated stores.
- Verify private-boundary denials with approved staging fixtures. Include the game SQLite files and journals, independent ledger, configuration, vendor sources, logs and backup location. Keep health checks and evidence free of real private values. Confirm both provider callbacks use the exact registered HTTPS origin and paths. Complete real Google and GitHub login, cancellation, separate-browser restoration, account isolation and conditional save checks with dedicated test identities on the staged candidate. Record observed status, versions and results through the original game tab. [SAVE acceptance](../SPEC.md) · [Staging evidence](evidence/spec001/staging.md)
- Confirm backup freshness, independent key and ledger recovery, retention coverage and the recorded rollback procedure on this host. Preserve the prior code, scoped site changes, tested recovery artifacts and their private locations. Only activate the accepted release and its arcade listing after the pre-publication gates pass. Public smoke and final reconciliation follow the recorded release sequence. [Recovery drill](evidence/spec001/recovery-drill.md) · [Execution sequence](../specs/001-physical-layer-underworld/tasks.md)

## Switch and recover

Drain game writes using the package's `private/server/bin/backup.php` command and the protected ops configuration. Gate game ingress and stop/drain old workers, including workers from an earlier version that may predate the drain. Verify there are no in-flight writes, capture and validate fresh game and independent ledger backups, then migrate or switch the public mapping, trusted PHP version path and running workers together. Verify the active release, API and last acknowledged save before resuming writes. If verification fails, keep ingress drained and retain the affected release for diagnosis.

When the previous code reads the current schema and content safely, restore its matched public and private code and keep the current database. For an incompatible change, use the verified coordinated rollback or forward repair in an isolated destination and check deletion markers and every current acknowledgement before any cutover. A stale pre-release database cannot replace newer acknowledged progress. Recheck the game, both providers, save revision, staging sentinels and the external deletion ledger after the switch. Record the selected target, times and outcome privately. [Drain, rollback and restore](operations.md) · [Observed rollback cases](evidence/spec001/recovery-drill.md)
