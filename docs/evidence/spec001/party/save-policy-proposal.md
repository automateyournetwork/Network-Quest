# T094 bounded recruit save-policy proposal

Status: coordinator-approved scope, not implemented. Wait for accepted T093 and
the integration GO. No save-v1 payload field changes are proposed.

The current trusted policy permits any character-owned ability at any level up to
`maxLevel`. Production characters have not yet been loaded, so this is presently
an unexercised relationship. With T093's two meaningful levels it would admit a
level-one record containing the level-two explanation ability.

Add `abilityIdsByLevel: Record<string, readonly string[]>` to each trusted recruit
policy. Generate an explicit entry for each authored level by taking the cumulative
set of that character's progression unlocks through that level. Reject duplicate,
missing, nonpositive, gapped, unsupported or foreign-character progression
definitions before generating the policy; never infer an unlisted level. Canonicalize
the authored row order without changing unlock membership.

The new-write JS and PHP validators require the saved level to have a policy entry
and the saved `abilityIds` set to equal the complete cumulative set for that level.
Set order is immaterial. Existing schema checks retain uniqueness and bounds.
`maxLevel`, owner membership and `progressFlagIds` checks remain. No numeric XP,
practice cursor, measurement baseline, hidden invitation receipt or extra slot is
saved. The generated policy remains trusted server/client metadata, never a field
that a snapshot can supply or override.

The explicit hypothetical migration fixture's valid saved recruit is level two
with one ability. Extend only its trusted test policy projection: the artificial
level-one helper has no unlocked abilities, and level two has the original ability.
Do not rewrite the original migration input, expected output or sealed fixture.
Apply the analogous explicit test-policy projection to the original service fixture
at its TS/PHP accessor boundaries; retain the JSON bytes and all expected cases.

Run identical snapshot bytes through JS and PHP for all nine production recruits:

| Saved level and abilities | Expected new-write result |
| --- | --- |
| Level 1, exact base ability | Accept |
| Level 1, base plus level-2 ability | Reject relationship |
| Level 1, level-2 ability alone | Reject relationship |
| Level 2, exact base plus new explanation | Accept |
| Level 2, only base | Reject relationship |
| Level 2, only explanation | Reject relationship |
| Level 2, another character's ability | Reject relationship |
| Level 3 or another unauthored level | Reject relationship |
| Level 0 | Reject schema |
| Duplicate ability IDs | Reject schema |
| Same exact set in reverse order | Accept |
| Unrecruited active ally, three active allies, duplicate active ally | Reject existing relationship/schema boundary |

Also capture a real progressed party through the actual save coordinator and
restore it; valid authored state must not be rejected because of policy drift.
Keep retained write receipts ahead of the new semantic policy exactly as the save
repository already requires. Do not regrade acknowledged writes under a newer
policy or change receipt/revision behavior.

## Isolated differential evidence

The preparation scripts write only beneath this evidence directory. They preserve
original source copies and make candidate copies with adjusted import/contract
paths pointing at the same unchanged save-v1 schema. The proposed production patch
contains none of those temporary path adjustments. No shared source has been
changed and no production policy file has been regenerated by this worker.

`level-policy-cases.json` binds literal acceptance/rejection categories to T093's
actual nine character/18 ability identities. Its 139 snapshots are explicitly
synthetic validator candidates, not gameplay proof. The exact same bytes go to JS
and isolated PHP 8.4.28 with only PATH/LANG/LC_ALL inherited; no HTTP, session,
account, credentials or database are involved.

- Existing implementations: 63 failed expectations/216 passed assertions. Both
  runtimes agree, exposing seven absent level checks for each of nine recruits.
- Isolated proposed implementations: 279 assertions passed across all 139 cases.
- Candidate generator over the frozen canonical T093 registry: 149 checks passed,
  including the same 139 JS/PHP cases using actual generated metadata and refusal
  of eight malformed progression definitions.
- Scoped strict TypeScript passes. Exact accepted JSON bytes and provisional
  validation status remain intact. Full matrices and initial failures are retained.

These results do not execute party gameplay, advance T094 acceptance or verify
transaction/receipt behavior; the shared integration must retain its existing
repository tests and policy-generation check when the coordinator authorizes it.
